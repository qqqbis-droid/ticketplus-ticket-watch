# Ticket Plus 六場雙層監測設計（2026-10-20）

## 目標和限制

- **唯一票況來源：Ticket Plus 官方網站**，不使用新聞、PTT、Discord 或第三方監票服務作票況來源。
- **設備與成本：只有 iPhone、無額外月費**；希望手機鎖定待機也收到 Telegram 推播。既有 Telegram 測試已成功，但真正監票尚未啟用。
- **僅唯讀：不自動購票、下單、登入、破解驗證碼或繞過 HTTP 403。**
- 六場：2026-12-12、12-13、12-15、12-18、12-19、12-20；沿用 `config/events.json` 中固定的 /order/ URL。
- GitHub Actions 最短可規劃 5 分鐘檢查，但不保證準時執行，也不能宣稱即時秒級通知。

## 監測信號（兩層獨立，不應只在首頁放行時才檢查個別頁）

| 層級 | 觀察位置 | 有效的正向訊號 | 不可通知 |
|---|---|---|---|
| A：活動首頁 | `/activity/` 下「活動介紹」的每張場次卡片 | 同一日期卡的「銷售一空」變成**可見、可按、且對應該日期的藍色**「立即購買／立即購票」 | 頁首全域購買按鈕、Loading、HTML 骨架、灰色不可用按鈕、缺少日期或卡片 |
| B：獨立場次 | 六個 `/order/` 頁各票區（需頁面允許取得且權限合適） | 有效票區內 `剩餘 N > 0`，同時票區可操作 | 只看到「立即購買」文案、0 張、必須登入、轉址、驗證碼、HTTP 403 |

**注意：** A、B 兩種訊號可能不同步；任何一種經過實站確認都可單獨構成不同等級的提醒。沒有實際驗證「藍色按鈕」與可售的關係前，不要把它宣稱成保證有票。

## 場次對應

利用 `config/events.json` 把每張卡的完整日期或可驗證的對應場次網址，對到固定 session ID；每張卡必須唯一對應一個場次。絕不可只依畫面位置、第 N 張卡片判斷日期。

- 日期規則要允許 `2026-12-18(五)`、`2026/12/18`、`12/18` 等展示形式；但缺年份時，只能在本活動及唯一匹配情況下判定。
- 不要對同一場次內 `status_text` 和全域按鈕混用。
- 針對 2026-12-20 台灣時間之後停止檢查。

## 伺服器端狀態機

`unknown`（網頁或資料讀取失敗）→ 不通知、不重置上一筆已知狀態。
`sold_out` → 記錄該場狀態為不可購買。
`available` → 只有相應層級的真實正向訊號驗證通過才通知。
`available` 持續 → 不重複發送；當之後恢復 `sold_out` 再重新變成 `available`，重新發送。
首次讀取就 `available` → 應發送一次，無需強迫先看到 `sold_out`。
兩層訊號須標記來源及置信度；兩層同時觸發可合併同一則場次通知。
通知發送失敗則不得記為已通知；避免通知失敗造成漏報。

## 目前實測阻礙與可行性結論

- GitHub Actions（一般及模擬 iPhone 瀏覽器）打開活動首頁皆停在 `Loading...`，找不到六場卡片；詳見既有 GitHub 執行紀錄。
- Network log 指出官方前端請求 `apis.ticketplus.com.tw/config/api/v1/getS3?.../event.json` 時失敗；後續匿名 HTTP 直連，獲得 **403 Forbidden**。
- 未登入的 `/order/` 會跳回活動首頁、彈出登入；無法讀取各票區庫存。
- 現有程式只是安全判斷框架，通過單元測試≠能在雲端監票。
- **現在不能啟用 schedule 或正式 Telegram 釋票通知。** 唯一可以完成的是已獨立測試成功的 Telegram 推播通道；須先取得網站允許、且從免費雲端實際可讀取的官方來源。
- 不主動猜測或嘗試繞過存取限制，不收集會員密碼、Token 或登入 Cookie。

## 未來正式啟用的驗收條件

1. 雲端實測在無驗證碼、無 403 的正常允許條件下取得六個完整日期/場次狀態（至少跨兩輪）。
2. 驗證各場卡片及票區的真實 DOM 位置，不單靠文字假設。
3. 使用模擬售罄／重新開放／載入失敗案例，測試個別場次對應、誤報與防重複。
4. 先手動測試 Telegram，確認收到含**正確場次網址**的測試訊息。
5. 最後才重新加入適當間隔的 GitHub schedule；記錄每次成功讀取與最後心跳，能辨認失效或網站改版。

**目前仍是設計規格，不是已啟用的票況監測。**
